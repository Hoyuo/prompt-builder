# prompt-builder — 대충 쓴 요청을 실행용 프롬프트로 바꾸는 스킬

프롬프트 엔지니어링을 모르는 사람을 위한 스킬입니다. "이거 버그났어"처럼 대충 쓴 요청을 받으면, 저장소에서 찾을 수 있는 것은 직접 찾고 모르는 것만 쉬운 말로 되묻습니다. 그렇게 해서 그대로 실행에 쓸 수 있는 프롬프트를 만들어 줍니다. 스킬이 만드는 것은 프롬프트까지이고, 실행은 따로 합니다.

```
사용자:    /prompt-builder 글 쓰는 화면 좀 편하게 해 줘

에이전트:  먼저 여쭤볼게요
           메모 쓰기 화면에서 가장 불편한 것 하나만 알려 주세요.
           (예: 저장 버튼을 찾기 어렵다, 글자가 작다)

사용자:    저장 버튼이 너무 아래 있어

에이전트:  이렇게 이해했습니다
           메모 쓰기 화면에서 저장 버튼이 맨 아래에 있어서 글이 길면 한참 내려가야
           누를 수 있습니다. 내려가지 않아도 저장 버튼이 보이게 옮깁니다.

           제가 정한 것
           - 저장 버튼을 화면 위쪽에 고정하는 것으로 정했습니다. 다른 자리를 원하면 알려 주세요.

           프롬프트
           요청 원문: 글 쓰는 화면 좀 편하게 해 줘 / 저장 버튼이 너무 아래 있어
           상황: 메모 쓰기 화면에서 저장 버튼이 맨 아래에 있어서 글이 길면 한참 내려가야
             누를 수 있다. 내려가지 않아도 저장 버튼이 보여야 한다.
           목표: 메모 쓰기 화면의 저장 버튼을 스크롤 없이 누를 수 있는 자리로 옮긴다
           대상: notes/templates/editor.html, notes/static/editor.css
           완료 기준:
             - 글이 길어도 메모 쓰기 화면에서 내려가지 않고 저장 버튼이 보인다
               — 확인: 사람이 직접 — 긴 글을 넣고 메모 쓰기 화면을 열어 본다
             - 저장 버튼을 누르면 지금처럼 저장된다 — 확인: 기존 테스트 tests/test_editor.py
           검증: pytest
           제약: (요청·저장소 문서에 없음)
           가정:
             - 저장 버튼을 화면 위쪽에 고정하는 것으로 정함
           참고: notes/templates/editor.html의 저장 버튼
           작업 규칙:
             - 고치기 전에 대상 파일과 관련 코드를 직접 읽고 원인이나 현재 구조를 확인한다. 읽지 않은 코드를 추측해서 고치지 않는다.
             - 완료 기준을 채우는 데 필요한 만큼만 바꾼다. 요청에 없는 정리·리팩터링·기능 추가는 하지 않는다.
             - 다 고친 뒤 완료 기준을 하나씩 '확인'에 적힌 방법으로 확인하고 검증 명령을 실제로 돌린다. 테스트를 통과시키려고 값을 끼워 맞추지 않는다.
             - 결과는 완료 기준별로 보고한다: 확인한 방법, 돌린 명령, 결과. 직접 확인하지 못한 기준은 못 했다고 쓰고 사용자가 무엇을 해 보면 되는지 적는다.
             - 대상 밖을 고쳐야 하거나 가정이 틀린 것 같으면 멈추고 묻는다.
             - 커밋·push·PR·배포·삭제는 사용자가 그 작업 이름을 들어 승인했을 때만 한다.

           맞으면 이 프롬프트를 그대로 쓰시면 됩니다. 제가 잘못 이해한 곳이 있으면 말씀해 주세요.
```

(위 예시는 읽기 쉽게 몇 줄을 접었습니다. 실제 프롬프트에서는 완료 기준 한 줄에 `— 확인:`까지 이어 씁니다.)

## 왜 필요한가

대충 쓴 요청에는 무엇이 문제인지, 어디인지, 무엇이 되면 끝인지가 없습니다. 모델은 그 빈칸을 추측으로 메웁니다. 그러면 엉뚱한 파일을 고치거나, 덜 하고 멈추거나, 확인해 보지도 않고 "완료"라고 보고하게 됩니다.

이 스킬은 그 빈칸을 세 가지 방법으로 채웁니다.

1. **저장소에서 찾습니다.** 화면·기능 이름, 고칠 파일, 검증 명령, 지켜야 할 규칙을 먼저 찾습니다.
2. **못 찾는 것만 묻습니다.** 한 번에 하나나 둘만, 사용자가 답할 수 있는 평소 말로 묻습니다. 파일 이름이나 설정처럼 사용자가 모를 것은 묻지 않습니다.
3. **정한 것은 가정으로 드러냅니다.** 요청에 없어서 스킬이 정한 것 가운데 사용자가 겪는 일이나 보게 될 결과에 관한 것은 모두 `가정:`에 적습니다. 사용자는 가정만 읽고 자기 뜻과 맞는지 답하면 됩니다.

경로·명령 확인과 프롬프트 점검처럼 기계적으로 할 수 있는 부분은 스크립트가 하도록 만들었습니다. 모델이 그때그때 다르게 판단할 여지를 줄이려는 것입니다.

## 만들어지는 프롬프트

| 칸 | 무엇을 쓰는가 | 왜 있는가 |
|---|---|---|
| `요청 원문` | 사용자가 쓴 말 그대로. 되물어 받은 답은 ` / `로 이어 붙임 | 실행하는 쪽이 원래 말을 보고 해석이 틀렸는지 알아챌 수 있게 |
| `상황` | 사용자가 쓰는 말로, 지금 어디에서 무엇을 하면 어떻게 되는지와 어떻게 되면 되는지 | 사용자가 읽고 "맞다"를 판단할 수 있는 부분. 코드 이름은 쓰지 않음 |
| `목표` | 무엇을 하는지 한 문장. 사용자가 보게 될 결과를 기준으로 씀 | 작업의 범위를 한 줄로 고정 |
| `대상` | 실제로 있는 파일 경로. 새 파일은 `(새 파일)`, 확인 못 한 것은 `(확인 필요)` | 엉뚱한 파일을 고치지 않게 |
| `완료 기준` | 다 된 뒤 사용자가 보게 될 결과. 줄마다 `— 확인:`을 붙임 | 무엇이 되면 끝인지를 미리 정함 |
| `검증` | 저장소에서 찾은 실제 명령 | 지어낸 명령으로 "통과"라고 보고하지 않게 |
| `제약` | 지켜야 할 것과 그 출처(`AGENTS.md —`, `요청 —`) | 사용자가 하지 않은 말을 한 것처럼 쓰지 않게 |
| `가정` | 요청에 없어서 정한 것 가운데 사용자가 겪는 일·보게 될 결과에 관한 것. 사용자가 맞다, 아니다를 답할 수 있는 말로 씀 | 사용자가 확인할 곳을 한데 모음 |
| `참고` (선택) | 먼저 읽으면 좋은 코드·문서 위치. 원인으로 보이는 곳은 그렇다고 밝혀 적음 | 실행하는 쪽이 헤매지 않게. 원인은 읽기만 한 짐작이라 실행하는 쪽이 확인하게 |
| `작업 규칙` | 고정된 여섯 문장 | 아래 설명 |

**`— 확인:`** 은 그 기준을 무엇으로 확인할지 적는 자리입니다. 기존 테스트가 그 동작을 검사하면 그 테스트, 없으면 테스트를 추가해 검증 명령으로, 화면 모양처럼 자동으로 볼 수 없으면 사람이 직접 어디에서 무엇을 해 보면 되는지 씁니다. "검증 명령이 통과한다"는 다른 것을 망가뜨리지 않았다는 뜻일 뿐이라, 그것만으로는 완료 기준이 되지 않습니다.

**`작업 규칙`** 은 이 프롬프트만 받은 쪽도 같은 방식으로 일하게 하려고 붙입니다. 고치기 전에 직접 읽기, 필요한 만큼만 바꾸기, 완료 기준을 `확인`에 적힌 방법으로 하나씩 확인하기, 기준별로 보고하기, 대상 밖이면 멈추고 묻기, 커밋·push 같은 작업은 이름을 들어 승인받기입니다. 문장은 바꾸지 않고 그대로 씁니다.

## 설치

`SKILL.md`(Agent Skills 형식)를 읽는 에이전트 도구라면 그 도구의 스킬 폴더에 `skills/prompt-builder` 폴더를 통째로 복사하면 됩니다.

```bash
# 예: 저장소에 넣기 (팀 공유, 커밋 대상)
mkdir -p .agents/skills
cp -r skills/prompt-builder .agents/skills/
```

- 스킬 폴더 위치는 도구마다 다릅니다(`.agents/skills/`, `.claude/skills/` 등). 쓰는 도구의 문서를 확인하세요.
- 보조 스크립트 위치는 스킬이 직접 찾습니다. 저장소 안을 먼저 찾고, 없으면 홈 폴더의 설정 폴더(`~/.이름/…/skills/prompt-builder/`)를 찾습니다. 어느 위치에 설치해도 `SKILL.md`를 고칠 필요가 없습니다.
- 스크립트를 못 찾으면 "…없음 — 건너뜀 (찾은 위치: …)"을 출력하고 스킬이 가리키는 말·끝이 없는 표현·새로 만드는 요청·위험 작업·작업 크기를 직접 점검합니다. `SKILL.md`만 등록해도 동작한다는 뜻입니다.
- 필요한 것은 `python3`(3.8 이상)뿐입니다. 표준 라이브러리만 씁니다.

## 쓰는 법

```
/prompt-builder 대충 쓴 요청
```

호출 방식은 도구마다 다를 수 있습니다(슬래시 명령, `@` 멘션 등). 요청은 `$ARGUMENTS` 자리로 들어갑니다. 이 자리표시자를 치환하지 않는 도구라면 스킬이 사용자 메시지에서 요청을 가져옵니다.

1. 요청을 넣어 부릅니다.
2. 무엇이·어디가·무엇이 되면 끝인지를 저장소로 알 수 없으면 질문이 한두 개 옵니다. 평소 말로 답하면 됩니다. 모르면 모른다고 답해도 됩니다. 그러면 가장 작은 해석으로 만들고 그렇게 정했다고 알려 줍니다.
3. 프롬프트가 나옵니다. "이렇게 이해했습니다"와 "제가 정한 것"을 읽어 보고, 잘못 이해한 곳이 있으면 말하세요. 고쳐서 다시 만들어 줍니다. 살펴보다 찾았지만 요청에 없어서 넣지 않은 문제는 "넣지 않은 것"에 따로 알려 줍니다. 원하면 그것도 프롬프트로 만들어 달라고 하면 됩니다.

- **실행은 따로입니다.** 스킬은 프롬프트를 만드는 동안 파일을 고치지 않습니다. 프롬프트를 복사해 다른 세션에 써도 되고, 같은 자리에서 "이대로 해 줘"라고 하면 그 프롬프트와 작업 규칙대로 작업합니다.
- **작업이 큰 경우:** "프롬프트 1/3, 2/3…"으로 나눠 줍니다. 앞 프롬프트의 결과가 뒤 프롬프트의 전제가 되게 순서를 정합니다. 실행할 때는 하나씩 고르세요.
- **되돌리기 어려운 작업:** push, 커밋, PR, 머지, 배포, 삭제, DB 변경 등은 작업 이름을 들어 승인해야 합니다. 요청이 그런 작업을 실제로 하라는 것이면 스킬이 따로 알립니다. 단어가 대상 이름일 뿐인 요청("삭제 버튼 만들어 줘", "PR 템플릿 고쳐 줘")은 위험 작업으로 보지 않습니다.
- **자동 호출:** 처음에는 꺼 두었습니다(`triggers: ["user"]`, `disable-model-invocation: true`). "프롬프트 만들어 줘"가 이미지 생성 프롬프트 같은 다른 요청에도 걸릴 수 있어서입니다. 써 보고 괜찮으면 `SKILL.md` 앞머리에서 그 두 줄을 지우세요.

## 구성

```
skills/prompt-builder/
├── SKILL.md            스킬 본문: 규칙, 절차 5단계, 프롬프트 형식, 내보내기 전 점검(lint), 예시 4개
├── prompt_helper.py    요청·저장소 단서 뽑기 (1단계)
└── prompt_lint.py      만든 프롬프트 점검 (4단계 끝)과 되묻는 질문 점검 (3단계) — prompt_helper.py를 함께 씀
tests/
├── test_prompt_helper.py
└── test_prompt_lint.py
```

### lint — 만든 프롬프트 점검

요청 분석은 키워드 추측이라 틀릴 수 있지만, 만든 프롬프트는 `요청 원문:`, `목표:`처럼 칸이 정해져 있어서 **칸 단위로 정확하게** 점검할 수 있습니다. 스킬은 프롬프트를 보여 주기 전에 lint를 돌리고 ✗가 있으면 그 칸만 고쳐 다시 돌립니다. **점검은 모두 3번까지만** 합니다. 3번째에도 ✗가 남으면 더 돌리지 않고 남은 내용을 사용자에게 알립니다.

**설계 원칙: ✗는 고칠 방법이 분명한 것만 냅니다.** ✗가 틀리게 나오면 모델이 ✗를 없애려고 멀쩡한 내용을 바꾸거나 `(확인 필요)`를 남발합니다. 그래서 애매한 것은 △로만 알립니다.

| 판정 | 점검 내용 |
|---|---|
| ✗ 오류 | 필수 칸(요청 원문·상황·목표·대상·완료 기준·검증·제약·가정·작업 규칙)이 없음, 비었음, 템플릿 자리표시자가 남음. 제약에 SKILL.md의 자리표시자(`(요청에 있던 문장 그대로)` 등)가 그대로 남음 |
| ✗ 오류 | 대상에 경로가 없음, 저장소 밖 경로, 폴더가 틀린 경로, 또는 저장소에 없는 경로 뒤에 `(새 파일)`·`(확인 필요)` 표시가 없음. 표시는 항목마다 따로 보며, `(새 파일)`이 붙은 항목은 같은 이름의 파일이 다른 곳에 있어도 새 파일로 인정. 괄호 안 설명과 `res.json()` 같은 호출 표기는 경로로 보지 않지만(`검색 화면 (notes/search.py)`·`[검색](notes/search.py)`처럼 괄호 안의 파일 경로는 확인하고, 있는 경로가 따로 있으면 괄호 안의 없는 경로는 ✗ 대신 △. `search.py(main logic)`처럼 이름에 붙은 설명은 이름만 남김. `@types/node` 같은 패키지 이름과 `$HOME/…` 환경 변수는 경로로 보지 않음), Next.js의 `app/orders/[id]/page.tsx`·`app/(shop)/cart/page.tsx`·`routes/users.$id.tsx` 같은 경로는 한 경로로 봄. `notes/search.py:12` 같은 줄 번호는 떼고 확인하며, `src/**/*.ts` 같은 glob은 맞는 파일이 하나라도 있으면 통과(없으면 △). 한글 경로(`문서/가이드/설치.md`)와 `Dockerfile` 같은 확장자 없는 파일도 인식. `LoginService.login()`, `response.data` 같은 코드 식별자도 경로로 보지 않음. 모양으로 알 수 없어도 저장소에 그대로 있는 이름(`.gitignore`, `build.gradle`, `go.mod`, `src/`, `tests`)은 경로로 인정 |

### prompt_helper — 요청·저장소 단서

| 확인 | 방법 | 정확도 |
|---|---|---|
| 빠진 항목 | 대상·완료 기준·검증·제약 표현이 요청에 있는지 | **참고용.** 키워드 기반이라 틀릴 수 있음 |
| 가리키는 말 | "이거", "그거", "여기", "뭐가", "아까", "지난번" 등. 무엇을 가리키는지 요청에 없는 말 | 참고용. 요청의 다른 말로 알 수 없으면 스킬이 묻는다 |
| 끝이 없는 표현 | "예쁘게", "편하게", "빠르게", "느려", "정리", "개선", "알아서" 등. 어디까지 하면 끝인지 없는 말 | 참고용. 스킬이 범위와 끝낼 조건을 먼저 좁힌다 |
| 새로 만드는 요청 | "붙여 줘", "버튼 추가해", "만들어 줘", "구현해" 등("연결해도", "추가했는데"처럼 버그 설명은 제외). 없던 것을 만들라는 말 | 참고용. 다 된 모습은 사용자만 알아서, 요청에 없으면 스킬이 묻는다 |
| 모호한 표현 | "알아서", "적당히", "깔끔하게", "지난번처럼" 등 | 참고용 |
| 위험 작업 | push·force·`reset --hard`·커밋·PR·머지·배포·릴리스·production/운영 반영·삭제·drop·마이그레이션 | 참고용. 단어만 보므로 놓치기도 하고("지워 줘"), 오탐도 있음("삭제 버튼"). 스킬이 실제 실행 요청인지 직접 판단함 |
| 작업 크기 | 목록 6개 이상 또는 4000자 초과 | 참고용 |
| 경로 | 요청에 나온 경로가 저장소 안에 있는지. 파일 이름만 있으면 저장소에서 찾음(대소문자 무시로 한 번 더, `node_modules`·`build` 등 제외, `.github`는 포함). 한글 경로는 붙은 조사를 떼며 확인. 점이나 슬래시가 든 낱말은 모양과 관계없이 저장소에 그대로 있으면 경로로 봄(`.gitignore`, `build.gradle`, `src/`). URL·이메일·공백 든 백틱·저장소 밖 경로는 제외 | **확정.** 파일 시스템 기준 |
| 검증 명령 | 루트와, 대상 경로에서 가장 가까운 하위 프로젝트의 설정 파일. `package.json` scripts(npm/pnpm/yarn/bun — 모노레포는 루트 lock 파일 기준, npm 기본 test 문구 제외), `gradlew`, `pom.xml`, `pubspec.yaml`(flutter/dart), pytest(실제 테스트 파일이 있을 때, uv), Cargo, Go, Makefile | **후보.** 설정 파일이 있다는 것만 보고 판단하므로 실행 전 확인 필요 |

한국어 조사가 붙은 경우(`Login.kt에서`, `push해줘`)도 잡습니다. 저장소 루트는 `--root`, git 최상위, 현재 폴더 순서로 정합니다. 결과 첫 줄에 루트가 나오고, git 저장소가 아니면 경고를 붙입니다.

```bash
python3 skills/prompt-builder/prompt_helper.py scan --text <<'PROMPT_BUILDER_EOF'
로그인 버그 고쳐 줘 알아서
PROMPT_BUILDER_EOF
```

키워드와 기준값은 두 파일 맨 위 "조정 가능한 설정"에 모여 있습니다. 이상한 판정이 나오면 그 요청을 `tests/`에 추가한 뒤 키워드를 고치세요.

### 질문 점검 (`--question`)

사용자에게 되묻기 전에 `python3 prompt_lint.py --question`에 질문 글을 넣으면 △만 냅니다(저장소는 보지 않음). 물음표 3개 이상(`??`·`?!`은 하나), 코드 표기, 개발 용어, 보기 없음(`(예:`, 목록, ` / `로 나눈 보기가 없음) 네 가지를 봅니다. 모델이 질문 앞에 "저장소를 살펴봤습니다" 같은 앞말을 붙이고 질문에 개발 용어를 섞는 일이 반복돼서, 프롬프트 점검처럼 마지막 줄로 답 형식을 알려 줍니다.

- 모노레포

## 권한 설정에 대해

`allowed-tools`에는 읽기·검색 도구만 넣고 셸 실행 도구는 일부러 넣지 않았습니다. 여러 도구에서 `allowed-tools`는 제한이 아니라 **자동 승인 목록**이라, 셸 실행을 넣으면 스킬이 도는 동안 `git push` 같은 명령도 확인 없이 실행될 수 있기 때문입니다. 그래서 보조 스크립트를 돌릴 때마다 권한 확인 창이 뜰 수 있습니다. 거슬리면 셸 실행을 추가하되, 그 대신 도구의 권한 설정으로 push·배포 명령을 막는 것을 권합니다.

도구 이름 표기(`read`, `Read` 등)는 도구마다 다를 수 있습니다. 맞지 않는 이름은 무시되고 그 경우 권한 확인 창이 뜨는 차이만 있습니다.
