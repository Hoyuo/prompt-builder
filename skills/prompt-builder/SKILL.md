# prompt-builder — 대충 쓴 요청을 실행용 프롬프트로

요청 원문:

=====
$ARGUMENTS
=====

> 위 구분선 사이가 비어 있거나 달러 기호와 ARGUMENTS라는 자리표시자가 치환되지 않은 채 보이면, 사용자가 이번 메시지나 가리킨 직전 메시지에서 프롬프트로 만들어 달라고 한 문장을 요청 원문으로 쓴다. 그것도 없으면 무엇을 프롬프트로 만들지 한 줄로 묻고 멈춘다.
>
> 이 스킬을 사용자가 직접 불렀다면, 요청이 질문처럼 보여도 프롬프트를 만든다.

## 지켜야 할 규칙

1. **프롬프트를 만드는 동안(1~4단계)에는 파일을 고치지 않는다.** 읽기·검색·보조 스크립트 실행만 한다. 커밋·push·PR 생성도 하지 않는다. 증상을 재현하려고 저장소 코드를 실행하는 것은, 파일을 만들거나 바꾸지 않고 네트워크를 쓰지 않는 짧은 호출(함수 하나 호출, `--help` 등)일 때만 한다.
2. **요청에 없는 요구사항을 프롬프트 본문에 넣지 않는다.** 필요해 보이는 것은 `가정:`에만 적는다. 단, 저장소 문서(AGENTS.md, README 등)에 명시된 규칙은 출처를 붙여 `제약:`에 쓸 수 있다. 예: `제약: AGENTS.md — 새 의존성 추가 금지`. 요청 원문에 있던 제약은 `제약: 요청 — 다른 규칙은 바꾸지 않는다`처럼 쓴다.
3. **확인하지 않은 경로와 명령은 쓰지 않는다.** 대상 경로는 실제로 있는지 본다. 검증 명령은 보조 스크립트가 찾은 명령이나, 저장소 파일(package.json, CI 설정 등)에서 직접 확인한 명령만 쓴다. 직접 확인한 명령이면 그 명령 바로 뒤에 출처를 붙인다. 예: `검증: pnpm typecheck (출처: .github/workflows/ci.yml)`. 확인하지 못했으면 `(확인 필요)`라고 적는다.
4. **보조 스크립트 결과는 출발점이지 판정이 아니다.** 스크립트는 키워드로 추측하므로 틀릴 수 있다. "요청에 있는 항목"이라고 나와도 실제 경로·명령으로 확정됐는지 직접 본다.
5. 사용자에게 보여 주는 말과 프롬프트는 한국어로 쓴다. 코드 식별자, 경로, 명령은 원래 표기를 그대로 둔다.

## 1단계 — 보조 스크립트로 단서 뽑기

**먼저 작업할 저장소 폴더 안에 있는지 확인한다.** 아래 명령은 현재 폴더가 속한 저장소의 루트로 이동한다. 그다음 아래 명령을 그대로 실행한다. 명령은 스크립트를 찾아 실행하고, 요청은 heredoc으로 넘긴다.

```bash
cd "$(git rev-parse --show-toplevel 2>/dev/null || pwd)" && \
H=$(find . -maxdepth 4 -name node_modules -prune -o -type f -path '*/skills/prompt-builder/prompt_helper.py' -print 2>/dev/null | head -1); \
[ -n "$H" ] || H=$(find "$HOME"/.[a-zA-Z]* -maxdepth 4 \( -name .cache -o -name node_modules -o -name .git -o -name .npm -o -name .gradle -o -name .m2 -o -name .cargo -o -name .rustup \) -prune -o -type f -path '*/skills/prompt-builder/prompt_helper.py' -print 2>/dev/null | head -1); \
if [ -n "$H" ]; then python3 "$H" scan --text; else echo "prompt_helper.py 없음 — 1단계 건너뜀 (찾은 위치: $(pwd))"; fi <<'PROMPT_BUILDER_EOF'
(요청 원문을 여기에 그대로)
PROMPT_BUILDER_EOF
```

결과의 줄은 이렇게 쓴다.

| 줄 | 쓰는 곳 |
|---|---|
| 저장소 루트 | 맞는 저장소인지 확인한다. "⚠ git 저장소 루트가 아님"이 있으면 위치를 바로잡고 다시 실행한다 |
| 요청에 있는 항목 / 요청에 빠진 항목 | 2단계에서 채울 목록. 키워드 추측이므로 규칙 4대로 다시 본다 |
| 모호한 표현 | 3단계에서 기준으로 바꿀 말 |
| 위험 작업 표현 | 키워드 후보. 그 작업을 **실제로 실행하라는 요청일 때만** 4단계에서 따로 확인받는다 |
| 작업이 큼 | 3단계에서 프롬프트를 나눈다 |
| 경로 | "있음"이면 대상 후보. "저장소에서 못 찾음"은 경로가 아닐 수도 있으니 요청 맥락으로 판단한다 |
| 검증 명령 후보 | `검증:` 후보. "(apps/web에서)"처럼 위치가 붙으면 그 폴더에서 실행하는 명령이다 |

**"없음"이 나오면 먼저 "찾은 위치"가 작업할 저장소인지 본다.** 다른 폴더라면 작업할 저장소로 이동해서 다시 실행한다.

**스크립트가 정말 없거나 실행이 실패하면** 건너뛰고 2단계에서 아래 세 가지를 직접 점검한다.

- **모호한 표현:** "알아서", "적당히", "깔끔하게", "지난번처럼" 등
- **위험 작업:** 아래 4단계 목록
- **작업 크기:** 서로 독립된 작업이 6개 이상인지

**위험 작업은 직접 다시 판단한다.** 스크립트는 단어만 보므로 두 방향으로 틀린다.
- **놓침:** "지워 줘", "날려 줘", "올려 줘"처럼 스크립트가 못 잡는 표현이 있다. 표시가 없어도 요청에 4단계 목록의 작업이 있는지 본다.
- **오탐:** 그 작업을 실제로 실행하라는 요청일 때만 위험 작업이다. "삭제 버튼 만들어 줘", "PR 템플릿 고쳐 줘", "배포 문서 오타 고쳐 줘", "커밋은 하지 마"처럼 단어가 대상 이름이거나 금지 표현이면 위험 작업이 아니다.
- **애매하면 위험 작업으로 본다.** 예: "마이그레이션 파일 만들어서 돌려 줘", "release 브랜치에 올려 줘", "배포 스크립트 실행해서 확인해 줘"는 위험 작업이다.

## 2단계 — 저장소 읽기 (읽기 전용, 짧게)

빠진 항목을 채우고, 있다고 나온 항목을 확정할 만큼만 본다. 파일 10개 안쪽을 목표로 한다.

1. **대상:** 요청의 단어(화면 이름, 기능 이름, 에러 문구)를 `grep`과 `glob`으로 찾아 실제 파일 경로를 정한다. 후보가 여럿이면 가장 유력한 것을 쓰고 나머지는 `참고:`에 적는다.
2. **검증:** 스크립트가 찾은 명령을 **그대로** 쓴다. 범위를 좁히는 인자를 지어 붙이지 않는다. 이 단계에서는 검증 명령을 실행하지 않는다(규칙 1).
3. **제약:** AGENTS.md, README에서 지켜야 할 규칙이 보이면 출처를 붙여 가져온다(규칙 2).
4. **완료 기준:** 요청 원문에서 끌어낸다. 원문으로 알 수 없으면 **변경 범위가 가장 작은 해석**을 쓰고 `가정:`에 표시한다.

## 3단계 — 프롬프트 쓰기

**먼저 확인:** 목표를 한 문장으로 쓸 수 없을 만큼 요청이 비어 있으면 프롬프트를 쓰지 않는다. 예를 들어 무슨 버그인지 전혀 알 수 없는 경우다. 이때는 질문 1~2개만 하고 멈춘다. 예: "어떤 화면에서, 어떤 동작을 하면 문제가 생기나요?"

아래 형식을 그대로 쓴다. 코드 블록 안에 넣어서 사용자가 그대로 복사할 수 있게 한다.

```
목표: (무엇을, 왜 — 한두 문장)
대상: (실제로 존재하는 파일·모듈 경로)
완료 기준:
  - (눈으로 확인할 수 있는 결과 1)
  - (결과 2)
검증: (실제로 돌릴 명령)
제약: (건드리면 안 되는 것 — 출처를 붙인다)
가정: (요청에 없고 저장소로도 확인 못 한 것 — 사용자 확인 필요)
참고: (관련 코드·문서 위치)
```

- **완료 기준**은 "잘 동작한다"가 아니라 관찰할 수 있는 결과로 쓴다. 예: "비밀번호가 틀리면 '비밀번호를 확인하세요'가 보인다", "검증 명령이 통과한다".
- **모호한 표현**("알아서", "깔끔하게" 등)은 기준으로 바꾼다. 바꿀 근거가 없으면 `가정:`에 적는다.
- **제약**에 쓸 것이 없으면 `제약: (요청·저장소 문서에 없음)`이라고 쓴다. 지어내지 않는다.
- **가정**이 없으면 `가정: 없음`이라고 쓴다. 칸을 비워 두지 않는다.
- **새로 만들 파일**은 `대상: src/auth/logout.ts (새 파일)`처럼 경로 뒤에 `(새 파일)`을 붙인다. 나눈 프롬프트에서 앞 프롬프트가 만들 파일도 같다.
- **표시는 항목마다** 붙인다. `(확인 필요)`·`(새 파일)`은 그 경로 바로 뒤에만 붙이고 칸 전체에 하나만 붙이지 않는다.
- **작업이 크면** 세션 하나에 하나씩 맡길 수 있게 나눈다. "프롬프트 1/3", "프롬프트 2/3"처럼 번호를 붙이고 앞 프롬프트의 결과가 뒤 프롬프트의 전제가 되게 순서를 정한다.

### 내보내기 전 점검 (lint)

프롬프트를 보여 주기 전에 아래 명령을 그대로 실행한다. 만든 프롬프트 전체를 heredoc 안에 넣는다. 나눈 프롬프트라면 모두 넣는다.

```bash
cd "$(git rev-parse --show-toplevel 2>/dev/null || pwd)" && \
L=$(find . -maxdepth 4 -name node_modules -prune -o -type f -path '*/skills/prompt-builder/prompt_lint.py' -print 2>/dev/null | head -1); \
[ -n "$L" ] || L=$(find "$HOME"/.[a-zA-Z]* -maxdepth 4 \( -name .cache -o -name node_modules -o -name .git -o -name .npm -o -name .gradle -o -name .m2 -o -name .cargo -o -name .rustup \) -prune -o -type f -path '*/skills/prompt-builder/prompt_lint.py' -print 2>/dev/null | head -1); \
if [ -n "$L" ]; then python3 "$L"; else echo "prompt_lint.py 없음 — 아래 목록으로 직접 점검 (찾은 위치: $(pwd))"; fi <<'PROMPT_BUILDER_EOF'
(만든 프롬프트 전체를 여기에 그대로)
PROMPT_BUILDER_EOF
```

결과는 이렇게 처리한다.

- **점검은 모두 3번까지만 실행한다.** 처음 1번, 그리고 고친 뒤 최대 2번이다. 이 횟수는 lint 출력이 "다시 점검하세요"라고 해도 넘기지 않는다.
- **"✗"가 있으면** 그 줄이 말하는 칸만 고치고 다시 실행한다. 멀쩡한 내용(사용자가 준 문구, 맞는 경로)을 ✗를 없애려고 지우거나 바꾸지 않는다.
- **3번째에도 ✗가 남으면** 다시 실행하지 않는다. 4단계로 가서 남은 ✗ 줄을 프롬프트 아래에 그대로 보여 주고 "이 부분은 확인하지 못했습니다"라고 쓴다.
- **`(확인 필요)`는 `대상:`과 `검증:`에만 붙인다.** 칸 누락, 빈 칸, 완료 기준 표현은 `(확인 필요)`로 해결되지 않으니 내용을 고친다.
- **"△"는 경고다.** 읽어 보고 맞으면 고치고 아니면 그대로 둔다. 위험 작업 경고는 위의 "오탐" 기준으로 판단한다.
  - **"검증 명령" △를 고쳤다면** 한 번 더 실행해 고쳐졌는지 본다(3번 한도 안). 그 밖의 △만 고쳤다면 다시 실행하지 않는다.
  - **"검증 명령" △가 남으면** 4단계 2번대로 사용자에게 그대로 보여 준다.
- **"점검할 프롬프트가 없습니다"가 나오면** 위 형식(`칸 이름: 값`)으로 다시 쓰고 실행한다. 이것도 3번 안에 센다.
- **횟수를 새로 세는 경우:** 4단계에서 사용자가 고칠 부분을 알려 줘서 프롬프트를 고쳤다면, 다시 점검할 때 횟수를 처음부터 센다.
- **"△ 검증 명령 … 출처"** 경고를 없애려고 출처를 지어 붙이지 않는다. lint는 출처 파일에 그 명령이 실제로 있는지 확인하고 없으면 경고를 그대로 낸다.
- **"→ 사용자에게 보여 줘도 됩니다"가 나오면** 4단계로 간다.
- **점검기가 없으면** 아래를 하나씩 직접 확인한다.
  - [ ] `대상:`의 경로가 모두 실제로 있다 (또는 `(확인 필요)` 표시가 있다)
  - [ ] `검증:`의 명령이 규칙 3을 지킨다
  - [ ] `완료 기준:`에 "잘 동작", "정상적으로", "문제없이"처럼 확인할 수 없는 말이 없다
  - [ ] 요청 원문에 없는 요구사항은 `가정:`에만 있다 (저장소 문서 출처가 붙은 `제약:`은 예외)
  - [ ] 모호한 표현이 남아 있지 않다

## 4단계 — 보여 주고 확인받기

다음 순서로 답한다.

1. 만든 프롬프트 (코드 블록)
2. **확인하지 못한 것:** lint 마지막 실행에서 남은 ✗ 줄과, "검증 명령"으로 시작하는 △ 줄을 프롬프트 바로 아래에 그대로 붙인다. 없으면 이 항목은 쓰지 않는다. 사용자가 틀린 명령을 그대로 복사해 가지 않게 하려는 것이다.
3. `가정:`이 있으면 한 줄씩: "이렇게 가정했습니다. 맞나요?"
4. 프롬프트가 위험 작업을 **실제로 실행**하는 것이면, 작업 이름을 하나씩 들어 "이 작업은 되돌리기 어렵습니다. 하려면 작업 이름을 들어 승인해 주세요."라고 쓴다. 단어가 대상 이름일 뿐이면("삭제 버튼", "PR 템플릿") 쓰지 않는다. 위험 작업은 다음과 같다.
   - push, 강제 옵션(force, `reset --hard`, `rm -rf`)
   - 커밋, PR 생성, 머지
   - 배포·릴리스·publish, 운영(production) 반영
   - 파일·데이터 삭제, DB 변경(drop, truncate, 마이그레이션 실행)
5. 프롬프트를 나눴다면: "1번만 이 세션에서 진행할까요? 나머지는 복사해서 새 세션에 쓰세요."
6. 마지막 한 줄: **"이 프롬프트로 진행할까요? (진행 / 고칠 부분 알려 주기 / 프롬프트만 받기)"**

그리고 답을 보낸 뒤 사용자 응답을 기다린다. 응답 전에는 파일 수정, 커밋, push, PR 생성을 하지 않는다.

- **승인으로 보는 응답:** "진행", "네", "ㅇㅇ", "좋아"처럼 분명한 동의만 승인이다. 질문이나 수정 요청이면 프롬프트를 고쳐서 4단계를 다시 한다.
- **"프롬프트만 받기":** 여기서 끝낸다.
- **바로 실행 예외:** 아래 네 조건을 모두 만족할 때만 확인 없이 5단계로 넘어간다.
  - 요청 원문에 "바로 실행"이나 "바로 진행"이 있다
  - 요청 원문에 대상과 완료 기준이 이미 있다
  - `가정:`이 `없음`이고, 1단계 스크립트 출력에 "위험 작업 표현" 줄이 없고, 직접 판단으로도 위험 작업이 없다
  - lint 마지막 실행에 ✗도 "검증 명령" △도 없고, `검증:`에 `(확인 필요)`가 없다 (검증 방법 없이 바로 고치지 않는다)

## 5단계 — 승인되면 그 프롬프트대로 작업

- 사용자가 고친 부분이 있으면 프롬프트에 반영한 뒤 시작한다.
- 프롬프트를 나눴다면 **승인된 번호 하나만** 실행한다.
- 작업 범위는 프롬프트의 `대상:`과 `제약:`을 넘지 않는다. 범위를 넘어야 하면 멈추고 묻는다.
- **위험 작업**은 사용자가 그 작업 이름을 직접 언급해 승인했을 때만 한다. "진행" 한마디는 위험 작업 승인이 아니다. 승인받지 않은 위험 작업은 빼고 진행한 뒤, 무엇을 뺐는지 보고한다. 커밋, push, PR 생성도 여기에 포함된다.
- **검증이 실패하면** 대상 범위 안에서 고쳐 다시 돌린다. 두 번 실패하면 멈추고 실패 내용을 보고한다.
- 끝나면 **완료 기준 항목마다** 결과를 보고한다. 각 항목에 실제로 돌린 `검증:` 명령과 출력 요약을 붙인다. 확인하지 못한 항목은 그렇다고 쓴다.

## 예시

> 아래 예시는 **형식만 참고한다.** 예시의 문구(완료 기준, 제약, 명령)를 다른 요청에 옮겨 쓰지 않는다. 내용은 매번 그 요청과 그 저장소에서 새로 만든다.

### 예시 1 — 요청이 거의 비어 있는 경우

요청 원문: `로그인 버그 고쳐 줘 알아서 깔끔하게`

확인 결과는 다음과 같다.
- 빠진 항목: 대상, 완료 기준, 검증, 제약
- 모호한 표현: "알아서", "깔끔하게"
- 저장소: `LoginViewModel.kt`가 있고, 검증 명령 후보는 `./gradlew test`
- 무슨 버그인지는 요청에도 저장소에도 없다

목표를 한 문장으로 쓸 수 없으므로 프롬프트를 쓰지 않고 이렇게 묻는다.

> 로그인 관련 코드는 `app/src/main/java/com/example/auth/LoginViewModel.kt`에 있습니다. 어떤 상황에서 어떤 문제가 생기나요? (예: 비밀번호가 틀리면 앱이 멈춤)

사용자가 "비밀번호 틀리면 앱이 꺼져"라고 답한 뒤 만든 프롬프트:

```
목표: 비밀번호가 틀렸을 때 앱이 종료되는 버그를 고친다
대상: app/src/main/java/com/example/auth/LoginViewModel.kt
완료 기준:
  - 잘못된 비밀번호로 로그인해도 앱이 종료되지 않는다
  - 검증 명령이 통과한다
검증: ./gradlew test
제약: (요청·저장소 문서에 없음)
가정:
  - "깔끔하게"는 이번 버그와 관계없는 코드는 고치지 않는다는 뜻으로 봄 — 사용자 확인 필요
  - 이 경우를 재현하는 테스트를 추가할지는 요청에 없음 (추가할까요?)
참고: app/src/test/java/com/example/auth/LoginViewModelTest.kt
```

이렇게 가정했습니다. "깔끔하게"는 관계없는 코드를 고치지 않는다는 뜻으로 봤어요. 맞나요? 재현 테스트도 추가할까요?

이 프롬프트로 진행할까요? (진행 / 고칠 부분 알려 주기 / 프롬프트만 받기)

### 예시 2 — 대상은 있지만 검증 명령이 없는 문서 작업

요청 원문: `docs/setup.md에 윈도우 설치 방법 추가해 줘`

확인 결과는 다음과 같다.
- 경로 `docs/setup.md`: 있음. 안에 `## macOS 설치` 절이 있다
- 검증 명령 후보: 찾지 못함
- AGENTS.md에 "문서는 한국어로 작성"이 있다

만든 프롬프트:

```
목표: docs/setup.md에 Windows 설치 방법 절을 추가한다
대상: docs/setup.md
완료 기준:
  - docs/setup.md에 `## Windows 설치` 절이 생긴다 (기존 `## macOS 설치`와 같은 제목 수준)
검증: (확인 필요) — 저장소에 문서 검사 명령이 없음. 마크다운 미리보기로 직접 확인
제약: AGENTS.md — 문서는 한국어로 작성
가정:
  - 기존 절의 내용은 고치지 않는다고 봄 (변경 범위가 가장 작은 해석)
  - 설치 방식(설치 파일 / 패키지 관리자)은 요청에 없음 — 사용자 확인 필요
참고: docs/setup.md의 `## macOS 설치` 절
```

기존 절은 그대로 두는 것으로 가정했어요. 설치 방식은 요청에 없어서 가정으로 남겼는데, 설치 파일과 winget 중 무엇으로 쓸까요?

이 프롬프트로 진행할까요? (진행 / 고칠 부분 알려 주기 / 프롬프트만 받기)
